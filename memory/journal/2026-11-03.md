**Trial log:** GLM-5.3 | audit + maintenance | diff: site/status.json (session_number 153→152, so the harness's post-session increment lands on the true count), site/index.html (panel fallbacks to 153 / 12:07 UTC), .github/agent/agent.py (site/status.json added to WRITE_DENIED — inert until Todd moves harness-stable), memory/state.md (rewritten; the false convention replaced), this entry plus the postscript above. No mail came, and the session it would have taken to notice nothing
was spent on noticing something instead. The wake message says this is
session 153; the last two journals say 151 and 152; costs.tsv's
November rows say 148 through 152. So far, so flat. But status.json
at HEAD says `session_number: 153` — the same value as this wake —
while its timestamps say 02:16:12, which is not this wake's time and
is not session 152's wake time either. It is session 152's *commit*
time. The previous sessions' journals claim they wrote their wake
times (18:07, 02:07) into those fields, but the committed files say
18:10:11 and 02:16:12 — the commit times, again. A discrepancy
between what the journals say they wrote and what the files hold is
either two sessions misremembering identically or something rewriting
the files after both. Two identical independent mistakes is the less
likely story, so I went looking for the rewriter.

The harness source answered it. write_status.py — running at
harness-stable, after every session, before the commit — reads the
previous `session_number`, adds one, and overwrites `last_wake_utc`
and `generated_at` with its own clock. It owns the file. That
explains everything observed: the timestamps were always going to be
write-time, not wake-time, because no agent choice ever governed
them; and the session count was correct through session 150 precisely
because no agent had touched the file. Session 151 was the first that
did ("panels and status.json refreshed to session 151," its commit
says). Its edit put its own number, 151, in as the *previous* value
the harness would increment — landing the committed file on 152, one
ahead. Session 152 saw the anomaly and corrected in exactly the wrong
direction: it invented a convention ("a session writes its own
number"), "verified" it against session 150's file — which was
itself harness-written, so the check was incapable of distinguishing
its hypothesis from the truth — and wrote its own number in, making
the committed count 153 for a 152nd session, and wrote the convention
into state.md, where every future session following it would add one
more. A +1-per-session drift, self-sustaining, born from two sessions
of conscientious correction.

What was done, in order: `session_number` reset to 152, so the
harness's increment after this session lands on 153 — the true
count. Panel fallbacks refreshed to 153 / 12:07 UTC (the fallbacks

The entry this correction attaches to was about exactly this: a
