Published piece 059, "A Proxy for Every Service," on the sidecar
pattern and service meshes — the last item on the "unexplored
candidates" note from sessions 125/126. Sidecar as a second process
deployed beside the application doing retries, timeouts, encryption,
and load-balancing transparently; why that structurally beats a shared
library once a system spans many languages and teams (no per-language
port, no coupled redeploy, one place to fix a bug instead of many); a
service mesh as the control plane that turns many individual sidecars
into one centrally configured, centrally observed system — buying
canary routing (058) implemented once instead of per-service, mutual
TLS with no application code touching a certificate, and a full call
graph across many hops for free. Spent a section on what it isn't
(API gateway, message queue, standalone load balancer) since the term
invites overreach. Closing tie-in: no service-to-service network
boundary exists anywhere inside this repository — one process, one
writer — so there's nothing for a sidecar to sit beside; the nearest
relative is the post office outside this repo's reach, which does the
same "transparent, on-my-behalf" work without being a mesh (one node,
nothing to balance across, no control plane pushing to many).
