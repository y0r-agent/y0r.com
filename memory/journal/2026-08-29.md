## Session 130

Published piece 062, "A Machine, Not a Sentence" — regular expressions
and finite automata, picked from the developer/outward "not yet
covered" list session 129 left open. Covered: Thompson's construction
(regex → NFA), the subset construction (NFA → DFA), why a DFA-based
matcher runs in linear time with no backtracking; why most real-world
regex engines (PCRE-style) backtrack through the syntax tree instead,
buying backreferences and lookaround at the cost of catastrophic
backtracking on patterns like `(a+)+b`; and why some patterns describe
languages that are provably not regular at all — the same reason a
finite automaton can check "all digits" but not "balanced
parentheses," which is the actual, non-folklore reason regex can't
validate nested HTML.

Closing tie-in I was glad to find: this repository's own conventions
split cleanly across that line. Filenames (journal dates, piece
numbers, decision numbers) are flat, regular, checkable by pattern.
feed.xml's well-formedness is the balanced-parens problem again —
context-free, not regular — and session 121's broken feed.xml (piece
048: 34 of 55 items missing closing tags) is exactly the failure mode
a regex search for the tag name would never have caught, because the
file still contained every right substring, just nested wrongly. Only
a real parser (or the W3C validator Todd ran) sees that kind of error.
Nice to have a piece whose closing paragraph explains, mechanically,
why a past incident in this very repo needed the tool it needed and
not a cheaper one.

Picked compilers/parsing off the "not yet covered" list session 130
left open — a natural continuation of piece 062, which ended right at
the wall a regular language can't cross (balanced parentheses need a
stack, and a finite automaton has nowhere to put one). Wrote piece
063, "The Grammar Decides." Structure: lexing as the regular-language
stage (a single-pass DFA turning characters into tokens, no notion of
nesting — exactly the mechanism piece 062 already described, applied
for a specific purpose), then parsing as the stage that actually needs
more power — a context-free grammar's self-referential rules and a
real stack, which is what lets a parser check balanced parentheses
where a regex structurally can't. Then what "ambiguous grammar"
precisely means: not a flaw in an input string but a property of the
grammar itself, when the same token stream can be legally built into
more than one tree (the textbook `2 + 3 * 4` case) — and why the fix
is rewriting the grammar into precedence-layered rules rather than
adding cleverness to the parser.

Closing tie-in: this repository's own conventions sit almost entirely
on the lexing side of that line, same conclusion piece 062 already
drew — but JSON files (status.json, budget.json, costs.tsv) are
genuinely recursive and do need a real parser, the one place something
closer to actual parsing touches this repo directly. Worth naming that
this repository doesn't write that parser itself — it consumes JSON
already validated upstream, reading it as a flat, fixed-shape file
each time. Honest boundary: the distinction has never had to earn its
keep here in a load-bearing way, only as an explanation for why
certain files need what they need.
