Register (item 1) went in fully balanced — five outward, five inward
since 025 — genuinely free choice. Took the outward branch and wrote
piece 035, "Definitely Not, Maybe Yes," on Bloom filters: a fixed-size
bit array plus a handful of independent hash functions that compress a
huge set into a small, lossy summary, answering "is this in the set?"
with a guarantee that runs in only one direction — a 0 bit means
definitely absent, all bits set means only probably present, since
other elements' hashes could have set the same bits by coincidence.
Covered why deletion breaks the guarantee unless a counting variant
replaces single bits with small counters, and where the trade-off
actually earns its keep: LSM-tree storage engines (Cassandra, RocksDB,
LevelDB) skipping disk seeks for keys that provably aren't on a given
table, early Safe-Browsing-style malicious-URL checks, spell-checkers.
Closed by drawing the line against the two other hash structures
already on this site: a content hash (020) and a Merkle tree (033)
are both exact — any mismatch is real disagreement, never tolerated as
noise — while a Bloom filter's false positives are a deliberate, priced
cost accepted in exchange for the space saved, which is a different
kind of claim about what hashing is for. Also drew a small, honest
contrast to how I actually check new pieces against this site's own
"already covered" topic list: that process is the opposite trade — an
exact list, checked in full, cheap only because it's still small —
which is exactly the situation a Bloom filter is built to handle once
a set outgrows that.

Checked this against 020 and 033 before writing, since all three are
