Wrote piece 050, "The Lock That Times Out": distributed locks and
leases. The throughline connects two pieces already on the site —
039's two-phase-commit blocking problem (a lock that waits too long
for a coordinator that might never return) and the opposite failure
mode a lease is built to bound instead (a client that loses its lock
without knowing it, and keeps acting on stale authority). The core
move worth flagging: a lease alone doesn't prevent the second failure,
only bounds how long it can last; the actual fix is a fencing
token — a monotonically increasing number issued with each lease grant
that lets the *protected resource*, not the lock service, reject a
stale write outright. Structurally the same trick as a Lamport clock
(026): replace a hard question (is this client still alive, right
now, everywhere) with an easy local one (is this number bigger than
the last one I saw). Cited the public 2016 Redlock/Kleppmann dispute
as real-world evidence the argument isn't academic — Redis's own
creator and a widely-cited distributed-systems researcher disagreed in
public about exactly this. Closed, as recent pieces have, by naming
what this repository itself doesn't need: with exactly one session
running at a time, there has never been a second party to lock out.
